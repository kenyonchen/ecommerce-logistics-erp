## 背景

跨境 ERP 的业务复杂度集中在**规则与流程**上：订单状态约束、审批流转、库存联动、费用与应收应付归集……这些规则如果散落在 Controller 里会随着需求增长迅速失控（典型症状：改一处状态流转要搜全仓）。

同时，系统需要服务于不同买家规模（从小卖家到代运营），多租户与多平台扩展能力是明确的长期目标。

需要一个**能承载复杂规则、且模块边界清晰**的结构。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 经典三层（Controller / Service / Dao）+ 贫血模型** | 上手快、代码量小 | 业务规则散落；多表联动逻辑集中在 Service 里膨胀；难以做单元测试与规则复用 |
| **B. DDD 四层 + 聚合/值对象/领域事件（选定）** | 规则内聚到领域对象；上下文边界清晰；天然支持事件驱动的跨模块联动 | 类数量多（当前 266 个主源文件）；需要 MapStruct / 双模型（领域模型 vs JPA 实体）带来映射成本 |
| C. 微服务拆分（每上下文一个服务） | 物理隔离彻底、可独立扩容 | 当前团队规模与交付节奏下，分布式事务与运维成本过高 |

## 决策

采用**选项 B**：单体应用内部使用 DDD 分层，并按业务划分为 9 个限界上下文。

分层约定：

| 层 | 包前缀 | 职责 | 禁止 |
|---|---|---|---|
| 接口层 | `interfaces` | HTTP 入口、DTO、`Result` 包装、全局异常处理 | 不得包含业务规则 |
| 应用层 | `application` | 用例编排、事务边界、事件发布 | 不得包含领域规则判断 |
| 领域层 | `domain` | 聚合根、实体、值对象、领域服务、领域事件、仓储接口 | 不得依赖 Spring / JPA |
| 基础设施层 | `infrastructure` | JPA 实体与仓储实现、MapStruct 映射、安全、消息、切面 | 不得反向定义领域规则 |

上下文划分（见 README 设计理念）：核心域 = 订单、物流；支撑域 = 仓储、产品、采购、财务、客户；通用域 = 平台集成、用户/租户。

## 理由

1. **规则内聚**：订单能否发货、采购能否审批这类规则，写在 `Order`、`PurchaseOrder` 与对应领域服务里，任何调用方都无法绕过（前提是接口层不要绕过，见 ISS-003）。
2. **边界清晰**：每个上下文拥有自己的聚合根与仓储，避免了"一张大表被所有人改"的耦合。
3. **为事件驱动预留位置**：已定义 22 个领域事件与 `DomainEventPublisher`，跨上下文联动（订单→库存→财务）可以后续用事件补齐而不推翻结构。
4. **单体先行**：在规模尚未验证前，用单体承载 DDD，保留未来按上下文拆分微服务的能力。

## 后果

### 正面

- 模块可独立演进：物流可以将 `LogisticsChannel` 做深，不影响订单；
- 领域规则可被单元测试直接验证（当前仅 Controller 有测试，ISS-028）；
- 新增"报表/看板"类需求可以走查询侧，不污染写模型。

### 负面 / 需要承担的成本

- **双模型映射成本**：领域模型 ↔ JPA 实体需要 MapStruct（12 个 Mapper），个别地方用反射注入私有字段（`OrderMapper`），可读性差；
- **类数量膨胀**：266 个主源文件，新人上手成本高，需要文档（本套文档即为此产生）；
- **规范依赖自觉**：分层约束没有静态检查手段（无 ArchUnit），需要靠 Code Review 与本文档约束。

### 必须遵守的约束与待办

| # | 约束 / 待办 | 关联 |
|---|---|---|
| 1 | 接口层不得直接修改聚合内部状态，必须调用领域方法（否则产生 ISS-003 这类绕过） | ISS-003 |
| 2 | 领域服务实现放领域层而非应用层（当前 Tenant/User/Role 例外） | ISS-027 |
| 3 | 所有聚合根统一继承 `BaseAggregateRoot`（当前 4 个例外） | ISS-025 |
| 4 | 补齐领域层与仓储层的单元测试 | ISS-028 |
| 5 | 引入 ArchUnit 做分层架构守护（可选） | — |

## 复审触发条件

- 上下文数量超过 ~12 个，或某个上下文需要独立扩容/独立团队交付（ → 考虑拆分为微服务）；
- 领域模型与持久化模型出现大量重复演进成本（ → 考虑放弃双模型，直接使用 JPA 实体承载领域行为）；
- 事件驱动需要跨进程可靠投递（ → 引入真正的消息中间件并把 RocketMQ 配置落地为生产/消费实现）。
