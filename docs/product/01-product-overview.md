# 01 · 产品概览

| 项 | 内容 |
|---|---|
| 产品名称 | 跨境大卖 ERP 系统（Ecommerce Logistics ERP） |
| 产品形态 | SaaS 多租户 Web 应用（用户端 + 平台管理端） |
| 目标客户 | 跨境电商大卖 / 中型跨境卖家 / 代运营服务商 |
| 当前版本 | v0.0.1（骨架阶段，**仅验证/演示可用，不具备生产可用性**） |
| 技术底座 | Java 17 + Spring Boot 3（DDD 分层）、React 19 + Vite + Ant Design 6、MySQL 8 |

---

## 1. 一句话定位

> **为跨境大卖提供"多平台接单 → 统一履约 → 物流可视 → 库存准确 → 财务闭环"的一体化后台。**

不是通用 ERP，而是**围绕跨境订单履约链路**做深：把散落在 Amazon / eBay / Shopify 等平台的订单，与公司的仓库、物流渠道、采购、财务串联成一条可追踪、可对账的流水线。

---

## 2. 业务背景与痛点

跨境电商大卖的典型现状：把同一批货铺到多个国家、多个平台上卖，后台却是"多套 Excel + 多个平台后台 + 物流商后台 + 财务软件"拼起来的。

| # | 痛点 | 具体表现 | 造成的后果 |
|---|---|---|---|
| P1 | **订单碎片化** | 每上一个平台就多一套后台，订单分散在 5~10 个系统 | 漏发、重复发货、客服查单要切 5 个界面 |
| P2 | **履约状态黑盒** | 货交给了物流商，轨迹只有物流商后台能看 | 买家问"我的货呢"，客服答不上来 |
| P3 | **库存不准** | 多平台共享库存，超卖靠事后发现 | 平台罚款、店铺绩效下降 |
| P4 | **物流成本失控** | 渠道众多（邮政小包/专线/海外仓/FBA），比价靠经验 | 毛利率被运费吃掉 3~8 个点 |
| P5 | **补货靠拍脑袋** | 断货与滞销并存 | 断货损失销售额，滞销占压现金流 |
| P6 | **财务算不清** | 平台回款、运费、采购款、退款在时间上错开 | 月结靠人工对表，利润算不精确 |
| P7 | **权限与数据隔离缺失** | 代运营团队、多个店铺混用一套账号 | 数据越权、责任无法界定 |

## 3. 目标用户

| 类型 | 规模假设 | 特征 |
|---|---|---|
| **跨境大卖** | SKU 1k+，日均订单 500+，多平台多店铺 | 有专职运营/仓储/财务团队，愿意为效率付费 |
| **中型跨境卖家** | SKU 数百，日均订单 50~500 | 3~20 人团队，正在从 Excel 转向系统化 |
| **代运营服务商** | 同时服务多个品牌方 | **强多租户、强数据隔离需求** |

> **暂不服务**：纯外贸 B2B、工贸一体的生产制造型企业、单平台小卖家（Excel 已够用）。

## 4. 产品目标与成功指标

北极星指标：**日均系统内闭环履约订单数**（订单在系统内从"待处理"流转到"已完成"，且生成了对应的财务流水）。

| 目标 | 描述 | 衡量指标 | 基线（当前） |
|---|---|---|---|
| O1 | 统一多平台订单入口 | 系统处理的订单占全部平台订单比例 | 0%（平台拉取仍为桩） |
| O2 | 履约过程可视化 | 可查询到实时轨迹的物流单占比 | 0%（无轨迹明细） |
| O3 | 库存可信 | 账实相符率（盘点差异率） | 不可测（无盘点闭环） |
| O4 | 物流成本可控 | 单均运费、渠道成本对比可见 | 部分（有运费计算无对照分析） |
| O5 | 财务自动闭环 | 自动生成的财务流水占比 | 0%（手工创建） |
| O6 | 补货前置决策 | 缺货预警提前天数 | 部分（有缺货状态无预警） |

**健康度指标**：订单查询响应 < 1s（1 万单量级）、列表页首屏 < 2s、核心接口可用率 ≥ 99.5%。

## 5. 产品范围（Scope）

### 5.1 In Scope（本期要做）

| 域 | 范围 | 子域类型 |
|---|---|---|
| 订单管理 | 订单创建、状态流转、取消、按客户查询、订单同步（平台拉取） | 核心域 |
| 物流管理 | 物流单、物流渠道、面单/标签、运费计算、轨迹状态跟踪 | 核心域 |
| 仓储管理 | 仓库、库位、库存台账、盘点、出入库与调拨、**缺货预警** | 支撑域 |
| 产品管理 | 产品、SKU、分类、**属性** | 支撑域 |
| 采购管理 | 采购单、审批流、到货入库联动 | 支撑域 |
| 财务管理 | 收支流水、订单对账、费用核算、报表 | 支撑域 |
| 客户管理 | 客户档案、沟通记录、客户分层 | 支撑域 |
| 平台集成 | Amazon / eBay / Shopify 等对接与自动同步 | 通用域 |
| 多租户与权限 | 租户、用户、角色、权限点 | 通用域 |

### 5.2 Out of Scope（明确不做）

| 不做的事 | 原因 |
|---|---|
| 生产制造 / MES / 委外加工 | 与跨境履约链路无关 |
| WMS 硬件集成（PDA、AGV、拣货波次算法） | 属于专业 WMS，本产品只做"库存台账层" |
| 广告投放与 AMS 优化 | 独立产品线 |
| 自建独立站/商城 | 公司的销售前端在第三方平台 |
| 税务申报 / 发票开具 / VAT | 强地区合规属性，交由专业财税工具 |
| 多语言前台与买家端门户 | 买家触达发生在第三方平台内 |
| 移动端原生 App | 本期只做响应式 Web |

## 7. 差异化价值主张（相对"Excel + 多个后台"）

| 维度 | 现状手工模式 | 本产品目标模式 |
|---|---|---|
| 接单 | 逐平台导出导入 | 平台自动拉取、订单归集到统一列表 |
| 发货 | 手工复制到物流商后台 | 系统内选渠道 → 生成面单 → 回写轨迹 |
| 库存 | 事后发现超卖 | 出库即扣减、缺货标记、到货上架回补 |
| 对账 | 月末人工对表 | 订单/物流/采购自动产生流水，按单据可追溯 |
| 成本 | 事后算毛利 | 单均运费与渠道维度可比 |

## 8. 当前阶段的重要约束（务必知悉）

作为产品经理，必须清楚**当前产品能力与上述目标之间存在显著差距**，这些差距会直接影响对外演示与交付：

1. **业务流程未闭环**：~~订单创建后不会自动占库存、发货后不会自动生成财务流水、采购到货不会自动入库——跨上下文联动目前是空实现。~~ → 🟡 **2026-01-25 复测：「空实现」已不成立，但三条断点里两条仍在。** 现状是 **4 个 MQ 消费者 + 进程内 `EventHandler`，其中 2 个真做副作用、2 个是只打日志的空壳**：<br>✅ 真实联动：`OrderCreatedEventConsumer:36-41` 订单创建 → 自动建物流单；`InventoryShortageEventConsumer:37` 缺货 → 自动建采购单。<br>❌ 仍是占位（原话照抄，代码里就写着）：`OrderStatusChangedEventConsumer:28`「仓储侧预留接口尚未实现，此处仅记录意图」→ **订单确认不占库存**；`LogisticsCompletedEventConsumer:27`「物流费用到财务结算记录的记账规则未定义，此处仅记录事件到达」→ **发货不生成财务流水**；采购到货也不触库存（`PurchaseApplicationService` 内无 `INBOUND`/库存写入调用）。<br>❌ 另加三点新问题：① **同源双通道**——进程内 handler 与 MQ 消费者对同一事件各做一次副作用，同时启用会重复建单（ISS-054，注释已写明并指向 [ADR-0006](../adr/0006-rocketmq-domain-events.md)）；② 消费者取不到租户时硬编码 `"default-tenant"`（`OrderCreatedEventConsumer:38`、`InventoryShortageEventConsumer:37` 直接写死实参）；③ `AFTER_ROLLBACK` 处理器只打日志（ISS-053）。详见 [`05-core-business-flows.md`](./05-core-business-flows.md) 的"断点"标注。
